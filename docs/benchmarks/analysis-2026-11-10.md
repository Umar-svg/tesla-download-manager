# Benchmark analysis: 2026-11-10

Raw data: [2026-11-10.json](2026-11-10.json). Generated tables: [2026-11-10.md](2026-11-10.md), from `tools/bench/run_bench.py --reps 3`.

- Machine: i7-1355U, 10 cores / 12 threads, 15.7 GiB RAM, SK hynix NVMe SSD, Windows 11, curl 8.21.0.
- Setup: the server is the Python probe server on the same machine over loopback.
- Integrity: all 42 runs of the reported pass, and the 42 runs of the earlier pass that exposed the connection-cap defect, had their SHA-256 verified against the server. For Tesla DM the file was also re-hashed independently from disk.

## Where multi-connection wins (the case it exists for)

Servers often cap the throughput of each connection. With a 4 MB/s cap per connection, 64 MiB:

| Connections | Median | vs curl (1 connection) |
|---|---|---|
| 1 | 16.94 s | 0.99× |
| 2 | 8.52 s | 1.97× |
| 4 | 4.33 s | 3.89× |
| 8 | 2.21 s | 7.60× |
| 16 | 1.24 s | 13.58× |

Scaling is close to linear. The gap from ideal (16×) is the probe round trip, the split ramp-up and the finalize step (about 0.06 s).

With 100 ms added before every response, 8 connections take 2.42 s instead of 2.21 s (6.98× curl). Each new segment request pays the delay once.

## Defect found by the benchmark (fixed)

The first pass showed 16 connections no faster than 8 (29.9 vs 30.2 MB/s). The cause had two parts:

1. The engine's connection pool used `PoolOptions::max_per_host = 8`, so 8 of the 16 requested fetches waited in the pool queue.
2. `active_connections` counted those queued fetches, so the report said 16.

The fix:

- The engine's pool now defaults to 32 per host (the per-download setting, 1–32, is the control).
- `active_connections` counts only connections that have received a response head.
- Regression test `EngineTest.SixteenConnectionsAreReallyUsed`: 0.83 s with 16 active, 3/3 runs. With the old cap temporarily restored it fails (1.59 s, 8 active).

## Where Tesla DM is slower (reported, not hidden)

**Unthrottled 1 GiB on loopback**

| | Last byte | Completed |
|---|---|---|
| curl | – | 1.84 s |
| Tesla DM, 8 connections | 1.68 s | 3.14 s |
| Tesla DM, 1 connection | 2.83 s | 4.38 s |

- With 8 connections, the bytes arrive about as fast as curl's (1.68 s vs 1.84 s).
- Tesla DM then spends about 1.45 s in finalize. That step runs `FlushFileBuffers` (1 GiB forced to the SSD), the rename, and a full SHA-256 re-read of the file. curl does neither: its data is still in the OS cache when it exits, and it doesn't verify. This is the cost of crash safety and integrity checking, which the spec requires.
- With 1 connection the receive path itself is slower: 2.83 s versus curl's 1.84 s. Likely contributors:
  - one extra copy of each chunk into the writer queue;
  - the single writer thread;
  - the read-gate round trip per 256 KiB read.

  None of these has been profiled yet.

**Many small files (100 × 1 MiB, 4 at a time):** 7.10 s against curl's 6.73 s, about 15 ms per file. That covers:

- a probe connection per file;
- the finalize thread, `FlushFileBuffers` and SHA-256 per file;
- DB writes;
- a scheduling gap of up to one 50 ms CLI poll.

## Follow-ups (not done in this phase)

1. Profile the single-connection receive path. Candidates:
   - avoid the copy into the writer queue (hand over pooled buffers);
   - larger reads when no rate limit applies;
   - batch adjacent writes.
2. Hash while downloading. Single-stream downloads can hash in order on the fly; segmented ones could hash finished, contiguous prefixes in the background. Either would remove most of the post-download re-read.
3. Consider making `FlushFileBuffers` on completion optional (a durability setting). It's on by default.
4. Small files: reuse keep-alive connections across downloads to the same host (the pool supports it; check the probe path).
5. Repeat on a real internet server and against IDM. The earlier IDM run was stopped, so IDM runs only with the user's agreement.
